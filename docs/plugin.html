01

설계 철학

플러그인 CLAUDE.md에 성문화된 동작 규칙. "동작하는 코드"가 아니라 "동작이 검증된 코드"를 목표로 합니다.

①듀얼 에이전트 사고

생성 시 "설계자"와 "검증자" 두 관점을 병행. 만들자마자 스스로 반증한다.

②항상 위임

오케스트레이터는 RTL을 직접 짜지 않고 반드시 전문 에이전트로 라우팅한다.

③계획 우선

생성 전 명확화 질문 → 아키텍처 계획. 코드는 그다음이다.

④검증 루프

lint → sim → formal → synth를 돌려 실패 시 에러를 3계층으로 번역·자동 수정 반복.

⑤합성 안전 패턴

always_ff/always_comb, active-low 비동기 리셋, 완전한 case/if로 래치를 원천 차단.

02

동작 원리 — 오케스트레이션

중심은 gf 오케스트레이터 스킬. RTL 요청이 들어오면 아래 파이프라인을 따릅니다.

1

SystemVerilog 작업 감지

요청이 하드웨어/RTL 작업인지 먼저 판별.

2

명확화 질문 필수

폭·깊이·리셋 방식·프로토콜·타깃 보드 등을 확정한다.

3

계획 수립

sv-planner / gf-plan — 아키텍처를 먼저 설계.

4

병렬 빌드

sv-orchestrator / gf-build — 설계를 모듈로 분해해 병렬 생성.

5

검증 루프

gf-lint → gf-sim → gf-formal → gf-synth. 통과할 때까지 반복.

실패 시 → gf-errors가 Verilator/Yosys 에러를 3계층으로 번역 → sv-debug / sv-refactor가 수정 → 재검증
✓

검증된 RTL 전달

lint-clean · 테스트 통과 · 합성 가능 상태로 인계.

보조 라우팅

gf-router(불명확한 요청 분류)와 gf-expand(옵션·트레이드오프 제시)가 흐름을 보조하며, 에이전트 스폰 시 세션 모델을 상속해 일관성을 유지합니다.

에이전트 스폰 (Agent Spawning)

오케스트레이터는 RTL을 직접 짜지 않고 Task 툴로 전문 서브에이전트를 실행(spawn)합니다. 각 에이전트는 독립 컨텍스트에서 돌고 구조화된 결과를 반환합니다.

"Task 툴로 스폰된다"는?

Task는 Claude Code(및 Agent SDK)가 제공하는 서브에이전트 실행 도구. 호출하면 지정한 종류(subagent_type)의 에이전트 인스턴스가 새로 만들어져(spawn) 작업을 하고 결과만 돌려줍니다. OS의 부모→자식 프로세스 생성에 빗댄 표현입니다.

특성의미
독립 컨텍스트부모 대화 히스토리를 물려받지 않음 → 자족적 프롬프트 필요
자체 도구 루프스스로 Read/Write/Bash/검색을 여러 턴 반복
결과만 반환내부 과정은 부모에 노출 안 됨, 최종 요약 하나만
모델 상속부모 세션과 동일 모델로 실행
병렬 가능한 메시지에서 여러 Task 호출 시 동시 실행

이점 — 컨텍스트 격리(시행착오가 부모를 오염 안 함) · 병렬성(독립 모듈 동시 생성) · 역할 분리(각자 전문 시스템 프롬프트·도구만 사용).

①

기본 패턴 — Task 툴

subagent_type: "gateflow:sv-codegen" + 자족적 프롬프트(스펙·인터페이스·제약·출력 경로). 서브에이전트는 부모 맥락을 자동으로 갖지 못하므로 모두 명시해야 한다.

②

세션 모델 상속

스폰된 에이전트는 부모와 동일한 모델로 실행돼 품질·일관성을 맞춘다. gf-lint/gf-sim 같은 순수 툴 실행은 모델 불필요.

③

단일 메시지 · 다중 Task 병렬 스폰

의존성 없는 모듈은 한 응답에서 여러 Task 호출로 동시 생성. sv-orchestrator는 설계를 Phase로 분해 → Phase 1(독립 리프) 병렬 → Phase 2(의존 모듈) 병렬.

④

결과 집계

모든 에이전트 반환까지 대기 후 ---GATEFLOW-RETURN--- 블록(STATUS/FILES_CREATED)을 파싱해 취합. 블록이 없으면 ERROR 처리, 파일 존재를 ls로 검증.

⑤

Phase Gate + 실패분만 재스폰

각 단계는 통과 조건을 만족해야 다음으로. 성공분은 유지하고 실패한 컴포넌트만 재스폰(모듈당 최대 2회).

자족적 프롬프트(self-contained prompt)란?

Task로 스폰된 에이전트는 완전히 새로운 독립 컨텍스트에서 시작합니다. 사용자·오케스트레이터의 대화, 명확화 답변, 앞서 정한 설계 결정 — 아무것도 자동 전달되지 않고 아는 것은 오직 prompt 뿐입니다. 그래서 프롬프트가 그 하나만으로 작업을 완수할 만큼 완결돼야 하며, 빠진 정보가 있으면 되물을 수 없어 추측(→오설계)하거나 실패합니다.

섹션담는 정보없으면
Component무엇을 만드는지(이름·정체)엉뚱한 모듈 생성
Specification동작·기능 요구(확정된 폭·깊이·리셋)스펙 추측 → 오설계
Interface포트·파라미터·프로토콜상위 모듈과 배선 불일치
Constraintslint-clean, 네이밍 규칙, 공용 타입스타일 위반 → 재작업
Output정확한 파일 경로산출물 미검출/오배치

명확화 질문을 스폰 전에 반드시 하는 이유가 이것 — 그 답변이 Specification·Interface를 채운다. 병렬 스폰 시에도 각 프롬프트가 자족적이어야 에이전트들이 서로 맥락을 몰라도 인터페이스가 맞물리고, Output 경로가 명확해야 ls로 산출물을 검증해 집계로 이어진다.

집계 분류조건조치
ALL_PASS전부 complete다음 단계 진행
PARTIAL_FAIL일부만 실패성공분 유지 · 실패분만 재스폰(≤2회)
ALL_FAIL전부 실패사용자에게 질문(스펙/환경 문제)

핵심 — ① 위임 · ② 자족적 프롬프트 · ③ 세션 모델 상속 · ④ 단일 메시지 병렬 스폰 · ⑤ 구조화 반환 블록 집계 · ⑥ 실패분만 재스폰. 관문형(Phase Gate) 파이프라인.

에이전트 / 20

특정 전문 영역을 담당하는 서브에이전트. agents/*.md의 frontmatter로 정의됩니다.

네이밍 규칙 — sv- vs gf-

접두사가 곧 아키텍처 계층을 나타냅니다. sv-는 누가(역할·도메인), gf-는 제품 표면(어떻게 불리나).

sv-작업자 에이전트

SystemVerilog RTL 도메인 전문가. agents/에 있고 Task로 스폰됨. 도메인이 다르면 접두사도 다름 — vhdl-, pcb-.

gf-GateFlow 네임스페이스

사용자가 부르는 진입점 — 슬래시 커맨드(21개 전부)·스킬. 이름 충돌을 피하는 네임스페이스. 유지보수 에이전트 gf-auditor/gf-pluginfixer도 포함.

핵심은 같은 기능이 두 접두사로 짝을 이루고 gf-(진입점)가 sv-(작업자)에게 위임한다는 점입니다:

사용자 진입점 (gf-)실제 작업자 (sv-)

IP 블록 라이브러리 / 8

각 블록은 RTL + 테스트벤치 + formal 속성 + 문서 + 메타데이터가 한 세트인 검증된 드롭인 컴포넌트입니다.

블록 해부 — 한 블록 = 6개 파일

ip/<block>/
├── block.yaml              # 메타데이터 (파라미터·포트·formal 증명·의존성)
├── rtl/<block>.sv          # 합성 가능한 RTL 소스
├── tb/tb_<block>.sv        # 자가검증 테스트벤치
├── formal/<block>_props.sv # SVA 속성 (assert property)
├── formal/<block>.sby      # SymbiYosys 증명 설정
└── README.md               # 인스턴스화 예시 + 검증 명령

block.yaml — 기계가 읽는 계약

단순 설명이 아니라 포트 폭을 파라미터로 표현하고 증명할 불변식을 목록화한 계약. sv-ip-scanner가 이를 읽어 포트 매칭·자동 삽입에 활용합니다.

parameters:
  WIDTH: { type: int, default: 8,  description: "Data width in bits" }
  DEPTH: { type: int, default: 16, description: "FIFO depth (power of 2)" }
ports:
  - { name: wr_data, dir: input,  width: WIDTH }   # 폭을 파라미터로 표현
  - { name: full,    dir: output, width: 1 }
formal_proofs:
  - p_no_overflow:  "FIFO never accepts writes when full"
  - p_no_underflow: "FIFO never allows reads when empty"
  - p_ptr_range:    "Pointer difference never exceeds DEPTH"

gf-ip — 라이브러리 조작

동작하는 일
/gf-ip list모든 블록의 이름·설명·검증 상태 표시
/gf-ip info <block>파라미터·포트·formal 증명·의존성 상세
/gf-ip add <block>블록을 현재 프로젝트에 설치 (아래 6단계)

add 흐름 — ① block.yaml 읽기 → ② rtl/*.sv→프로젝트 rtl/ → ③ tb/*.sv 복사 → ④ formal/* 복사 → ⑤ .gateflow/project.yaml의 ip_blocks에 추가 → ⑥ README 인스턴스화 예시 표시.

자동 탐지·자동 채움

수동 add뿐 아니라 sv-ip-scanner / gf-ip-detect / /gf-detect가 코드베이스를 스캔해 정의 없는 모듈·스텁·CDC 위반을 찾아 라이브러리 블록으로 자동 채움을 제안합니다 (예: CDC 위반 → cdc_2ff/cdc_handshake 삽입 유도).
